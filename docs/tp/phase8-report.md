# Phase 8 — Qwen3.8-27B TP=2 whole-model eager parity

Status: PASS for batch-one, short-context whole-model eager parity after the pre-commit review fixes. Both rank processes exited 0. This is a standalone GPU gate, not scheduler/serving integration or a performance result.

## Scope and ownership

`crates/paddock-engine/examples/qwen35_model_tp.rs` runs two rank processes using the Phase 2 TCP bootstrap and Phase 3 NCCL communicator. `gpu_model/qwen35/tp_model.rs` composes the accepted rank-local FFN, GQA/paged-KV and DeltaNet primitives through all 64 backbone layers. Embeddings, norms and output head are replicated; projection weights, KV payloads and recurrent state are rank-local. Rank 0 additionally loads a full-weight `GpuQwen35` model solely as the TP=1 oracle.

The gate feeds prompt `[1, 2, 3]` and two greedy continuation tokens as five one-token steps, twice with logical KV and recurrent-state reset. Configuration: batch 1, FP16 KV, max context 16, `PADDOCK_NO_SPEC=1`, no TP graph capture. This is not a native multi-token prefill test. The eager TP=1 oracle calls `forward_one_no_graph`; after the two TP passes, rank 0 resets that oracle and calls normal `forward_one` on the same five tokens to exercise first-token CUDA-graph capture and four replays. Rank 1 compares every logit's exact F32 bits with rank 0's TP logits on every step and independently checks exact reset replay; checksums are diagnostic only.

## Mixed-quant correction

Pinned GGUF: `Qwen3.8-27B-UD-Q4_K_M.gguf`, SHA-256 `322e194ff79741c7baa497c240f677f54b201b0efab44ca8e50f122b39123482`. The prior inventory of 64 backbone layers found 135 mixed dense projections: IQ4_XS 117, IQ4_NL 7, IQ3_S 4, Q3_K 7. The initial Phase 8 fallback unnecessarily allocated full-matrix FP32 scratch and dequantized these tensors on every token, including in the shared TP=1 decode path. Source review found that `packs/cuda/src/quant/kquant.cuh::pd_kquant_gemv` already has an IQ4_XS branch and routes IQ4_NL, IQ3_S and Q3_K through `pd_kq_iq_dense_gemv_f32` (`iquant_dense.cuh`). `qwen35/ops.rs::gemv_any` now dispatches all resident `QuantW::Kq` tensors to that dtype-aware direct GEMV; Q8_0 retains its separate repacked GEMV. The FP32 dequant/GEMM helper remains for other existing call paths, but this one-token dispatcher no longer allocates/dequantizes a whole weight per call. The TP loader still preflights `kq_params` coverage for dense projections and the head; the DeltaNet shard loader accepts its checked repackable formats. Broader checkpoint/pack compatibility is not claimed.

## Limits and next gate

The result covers one five-token batch-one eager sequence and reset replay, FP16 KV, a single physical page and the pinned GGUF. It does not validate whole-model native prefill, page crossing/prefix adoption, long-context capacity, multiple slots or requests, production worker/scheduler synchronization, TP graph capture, offload, speculation or throughput. The TP=1 graph check validates this pinned single-request path, not every serving configuration. Phase 9 and broader optimizations remain separate work.
