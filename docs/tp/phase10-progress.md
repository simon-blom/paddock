# Phase 10 progress — two-slot eager continuous-batching integration

Status: two-Spark max-batch=2 eager serving exercised against a separate TP=1 HTTP oracle; this is still **not** a Phase 10 async/overlap acceptance report.

Rank 0 retains the existing engine scheduler, admission, cancellation, and sampler. A `--max-batch 2` TP=2 run elects the ordinary batched loop rather than the Phase 9 serial loop. The scheduler's dense high-water rows are translated to ordered active slot/token/position rows; holes are omitted and logits are returned at the original slot indices. Prefill uses the generator's per-prompt default (eager token steps), and each decode row runs the accepted whole-model rank-local TP primitives in the same order on both ranks. This is continuous admission and batched *scheduler* execution, not a fused GPU batch or nonblocking forward.

Rank 0 authorizes logical paged-KV Ensure/Release/Flush events; rank 1 mirrors and checks sequence, slot order, position and resulting KV snapshot before its next collective. A slot release resets its DeltaNet recurrent/conv state without touching surviving slots; full reset clears every slot. Each GQA layer has slot-indexed block tables and rank-local payload. Both ranks retain Phase 9 pinned checkpoint/pack/context bootstrap, FP16 KV, eager kernels and two-rank NCCL collectives. TP graph capture, speculation, vision, offload and companion models remain excluded.

Host checks: `cargo check -p paddock-runner --all-targets`; `cargo test -p paddock-engine --lib` (422 passed); `cargo test -p paddock-runner --lib` (506 passed); `cargo test -p paddock-dist` (18 integration tests passed); `git diff --check`. New host tests cover sparse slot membership, mirrored two-slot release/reuse with a surviving slot, and ordered prepared/ready acknowledgements.

Two-Spark smoke (release runner SHA-256 `eba836b6d65bd048c925441a1c2a2b0769c0a1b9ba660bbb2e8dec6ef719db26` verified on both nodes, pinned GGUF SHA-256 `322e194ff79741c7baa497c240f677f54b201b0efab44ca8e50f122b39123482`, pack SHA-256 `059bb62d2e6d863b32ac47208d29da7492618b2fa33015a3ee0ad6fe2a9c4d54`): max_ctx=48, max_batch=2, no speculation, FP16 KV, RoCE interface pins as in Phase 9. Concurrent `Hi`/`Hello` completions each returned `", I'm a 2"` with 1 prompt and 6 completion tokens. A streamed `Hi` request was closed after its first token while a 14-token prompt continued to 18 completion tokens across a logical KV page; the survivor returned `"\n\nThis is a classic example of a **pangram**—a sentence that contains every"`. Two concurrent 4-token requests after the cancellation each returned `", I'm a"`. A separately loaded TP=1 server with the same GGUF and pack reproduced the complete (non-cancelled) text and token counts for those prompts. Both TP=2 ranks and the TP=1 server exited 0 after graceful shutdown. This is HTTP text/count parity, not proof of identical token IDs, all logits, precise cancellation timing, or async overlap. An earlier launch failed closed on a stale serial-only load guard; it was fixed before the successful run.

A second two-Spark run with two 32-token greedy requests sampled `/metrics` during execution: `paddock_num_requests_running` reached 2 (observed values 0 and 2), both requests completed, and both ranks exited 0. This proves two scheduler slots were occupied concurrently, but the gauge alone cannot prove each observed instant was a fused GPU decode batch.

1. Assert rank-local logits/token-ID parity, cancellation while another slot is inside decode, release/reuse after that cancellation, and all-slot recurrent replay with a GPU harness. A TCP ACK timeout does not protect a hung collective.

This path still processes rows one at a time with host logits readback and waits for rank-1 completion for each plan. `supports_device_sampling`, `supports_decode_pipe`, and `supports_overlap` are deliberately not advertised.
